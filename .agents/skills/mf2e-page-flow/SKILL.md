# RN 页面功能开发流程

## 概述

本技能是 mf2e 项目开发一个 RN 页面功能的**端到端流程编排**。它以项目 README 中登记的文档资源为输入，把「布局还原 → 接口对接 → 交互开发 → 埋点 → 需求 review」串成一条可追溯的流水线，每一步产出可独立验收的成果。

它不复制各子技能的能力，而是负责：① 从 README 解析并**筛选出只属于目标页面的资源**；② 按依赖顺序调度各子技能；③ 在步骤间传递上下文（类型、接口、store、组件）；④ 最后对照需求整体复盘。

## 触发条件

- 用户说「开发 / 实现 / 搭建 / 写 XX 页面」「做 XX 页面功能」「实现 XX 需求页面」
- 用户提供了某个页面名或路由，要求从零到一完成该页面
- 即使用户没提设计稿 / 接口文档，只要目标是"完成一个页面"，也应触发本技能，由第 0 步去 README 里补齐资源

## 前置条件

- 已连接 Figma MCP（`get_design_context` / `get_screenshot` / `get_metadata`）
- 已连接模拟器 MCP（`@mf2e/simulator-screenshot-mcp`：`compare_with_design` / `screenshot_simulator` 等）
- 已连接 POPO MCP（`getContentByUrl`）——需求文档、接口文档等多以 popo 云空间文档提供
- 已连接 Chrome DevTools MCP——读取其他 http 形式的远程文档（wiki / gotest 等非 popo 文档）时使用
- 项目根目录存在 `README.md`，且「相关链接」章节登记了资源地址
- 用户明确「目标页面」是什么（页面名 / 路由 / 线上地址 page id）

## 总体流程

| 步骤    | 目标                                | 依赖资源  | 编排的技能                                                                      | 缺失处理                            | 详解                                       |
| ------- | ----------------------------------- | --------- | ------------------------------------------------------------------------------- | ----------------------------------- | ------------------------------------------ |
| 第 0 步 | 解析 README、定位目标页面、筛选资源 | README.md | —                                                                               | 资源缺失时提示用户                  | 见下文                                     |
| 第 1 步 | 还原页面布局与样式（视觉层）        | 设计稿    | mf2e-figma-implement、mf2e-falcon-rn、mf2e-rn-library、mf2e-compare-screenshot | 设计稿缺失 → 提示，询问跳过或补充   | [step-1](references/step-1-ui.md)          |
| 第 2 步 | 生成接口类型、端点、Mock、Store     | 接口文档  | mf2e-api-scaffold                                                               | 接口文档缺失 → 提示，询问跳过或补充 | [step-2](references/step-2-api.md)         |
| 第 3 步 | 集成接口数据 + 交互逻辑             | 交互稿    | mf2e-falcon-rn、mf2e-rn-library                                                 | 交互稿缺失 → 提示，询问跳过或补充   | [step-3](references/step-3-interaction.md) |
| 第 4 步 | 添加埋点                            | 埋点文档  | mf2e-falcon-rn（`@/utils/track`）                                               | **无埋点文档 → 直接跳过**           | [step-4](references/step-4-track.md)       |
| 第 5 步 | 对照需求整体 review 并修正          | 需求文档  | —                                                                               | 需求文档缺失 → 提示，询问跳过或补充 | [step-5](references/step-5-review.md)      |

> 步骤间有依赖：第 3 步依赖第 1 步的组件 + 第 2 步的 store；第 4 步依赖第 3 步的交互点；第 5 步依赖前四步的全部产物。**严格按顺序执行，不要跳步**。

## 分步执行与验收门（最高纪律）

本流程的价值在于**每一步的产出都可独立验收**，因此：

1. **分步交付，禁止合并**：严格按 0 → 1 → 2 → 3 → 4 → 5 单步推进，完成一步、停一步。**禁止把多个步骤合并成一次连续开发后统一交付**（例如一次性写完布局 + 接口 + 交互再汇报）。
2. **每步结束必须停等用户确认**：每步满足其详解文档末尾的「本步出口条件」后，输出该步验收摘要并**停下来等待用户确认**；用户确认后才进入下一步，未确认不得开工下一步。
3. **确认点独立，不合并**：第 0 步资源清单、第 1 步组件结构与截图校验询问、第 2 步接口清单、第 3 步交互清单、第 4 步埋点清单，各自独立向用户确认。**某个确认通过不代表后续步骤自动放行**——「组件结构确认」只代表第 1 步可以写代码，不替代第 2 步的接口清单确认。
4. **未明确答复 = 未确认**：用户空回复、含糊、未选择时视为未确认，继续追问，**不得默认跳过、不得默认继续**。第 1 步截图校验询问必须发生在**该步 UI 代码写完之后、进入第 2 步之前**，不得拖延到后续步骤。
5. **返工成本前置**：分步验收的意义是在代价最小的阶段纠偏（布局返工 < 接口返工 < 交互返工）。宁可多停一次，不要带病进入下一步。

## 第 0 步：解析 README 资源与定位目标页面

这是整个流程的入口，也是本技能区别于"单独调用各子技能"的关键。**必须先做，不要拿到用户一句话就直接写代码。**

### 0.1 读取 README 资源地址

1. 用 `read` 工具读取项目根目录的 `README.md`
2. 定位「相关链接」章节（标题形如 `## 相关链接`，兼容 `## 相关文档` / `## Resources` 等变体）
3. 在该章节下按标题提取五类资源地址，**以下面 README 的格式为准**：

   ```markdown
   ## 相关链接

   ### 需求文档

   <地址或空>

   ### 交互稿

   <地址或空>

   ### 设计稿

   <地址或空>

   ### 接口文档

   <地址或空>

   ### 埋点文档

   <地址或空>
   ```

4. 记录每个地址的**类型**：
   - `docs.popo.netease.com` 开头 → popo 文档，用 POPO MCP 的 `getContentByUrl` 读取（需求 / 接口文档多为这种）
   - 其他 `http(s)://` → 远程文档（wiki / mastergo / gotest 等），用 Chrome DevTools MCP 打开并读取页面内容
   - 本地路径（如 `docs/api.yaml`）→ 直接用 `read` 读取
   - 空白 / 无该标题 → **缺失**

> 后续各步读取五类文档时，统一按这里的地址类型选择读取方式（popo → POPO MCP、http → Chrome DevTools MCP、本地 → read），不必在各步重复判断。

### 0.2 缺失资源提示

解析完五类资源后，向用户报告「有 / 缺」清单：

```
📋 目标页面资源清单
- 需求文档：✅ https://...  /  ❌ 缺失
- 交互稿：  ✅ ...  /  ❌ 缺失
- 设计稿：  ✅ ...  /  ❌ 缺失
- 接口文档：✅ ...  /  ❌ 缺失
- 埋点文档：✅ ...  /  ❌ 缺失（无则第 4 步跳过）
```

**缺失处理规则**：

- **埋点文档缺失** → 第 4 步直接跳过，不阻塞流程
- **需求 / 交互 / 设计 / 接口文档缺失** → 提示用户对应步骤无法完整执行，询问是「补充地址后继续」还是「跳过该步骤先做能做的」。**不要默默跳过，也不要硬编造资源。**

### 0.3 定位目标页面并筛选文档内容

> 这是最容易出错的一环：README 里的文档通常覆盖**整个项目**（多个页面），而本次只开发其中一个。直接照单全收会把别的页面的接口、埋点、样式也做进来。

拿到每份文档后，先确定目标页面的"锚点"，再用它筛选：

1. **确定目标页面锚点**（多个来源取交集确认）：
   - 用户明确说的页面名 / 中文名（如「排行榜」「任务中心」）
   - 路由名（如 `rank`、`task-center`）
   - README「线上地址」里的 page id（如 `ntescommunity://nc/page?id=rank` 的 `rank`）
   - 设计稿中的画板 / 页面标题

2. **按锚点筛选各文档**：
   - 需求文档 → 找到目标页面的需求条目 / 功能点清单，忽略其他页面
   - 交互稿 → 找到目标页面的交互说明 / 页面流转，忽略其他页面
   - 设计稿 → 定位目标页面的画板 / 节点（Figma nodeId / MasterGo 页面），忽略其他页面
   - 接口文档 → 筛出目标页面会调用的接口（通常按接口的模块 tag / 路径前缀 / 注释里的页面名），忽略其他页面的接口
   - 埋点文档 → 筛出目标页面的埋点事件表，忽略其他页面

3. **拿不准时向用户确认**：文档里页面边界模糊（如同一文档里两个页面共用一个模块）时，把筛选结果列给用户确认，不要猜。

> 筛选结果会作为后续每步的"输入范围"。这一步做得准，后面五步才不会跑偏。

## 执行各步骤

第 0 步完成后，**严格按 1 → 5 顺序执行**，每步读对应详解文件：

1. **[第 1 步：还原布局与样式](references/step-1-ui.md)** — 设计稿 → RN 布局/样式（模拟器截图校验为可选环节）
2. **[第 2 步：生成接口与 Mock](references/step-2-api.md)** — 接口文档 → 类型/端点/Mock/Store
3. **[第 3 步：集成数据与交互](references/step-3-interaction.md)** — 交互稿 + store → 数据绑定 + 交互逻辑
4. **[第 4 步：添加埋点](references/step-4-track.md)** — 埋点文档 → `@/utils/track` 埋点（可跳过）
5. **[第 5 步：整体 review](references/step-5-review.md)** — 需求文档 → 逐条对照排查偏差并修正

每步读完详解文件后再动手，步骤内也有明确的"何时加载哪个子技能"。

> **验收门**：每步完成其详解文档末尾的「本步出口条件」→ 输出该步验收摘要 → 停等用户确认 → 再进入下一步。禁止跳步、禁止合并步骤、禁止把第 1 步截图校验询问拖到第 1 步结束之后。

## 收尾汇总

五步完成后，输出一份整体交付报告：

```
✅ 页面「<页面名>」开发完成

资源使用：
- 设计稿：<nodeId 或链接>（第 1 步）
- 接口：N 个（第 2 步）
- 交互：M 项（第 3 步）
- 埋点：K 个事件（第 4 步，若无则标注跳过）
- 需求 review：P 项通过 / Q 项修正（第 5 步）

产出文件清单：
<按步骤列出新增/修改的文件>

遗留事项（如有）：
<未完成项、剩余差异、需要用户确认的点>
```
