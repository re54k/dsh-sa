# 需求开发流程

## 概述

本技能是 mf2e 项目完成一个**完整需求**（涉及多个页面/弹窗）的端到端流程编排。以用户提供的四类原始文档为输入，把「PRD → 接口 → 页面归类 → 逐页还原 → 走查」串成一条可追溯的流水线，每一步产出可独立验收的成果，每步之间有强制的 review 门禁。

它不复制各子技能的能力，而是负责：① 按依赖顺序调度各子技能；② 在步骤间传递上下文（PRD、类型、接口、store、manifest）；③ 在每步完成后停下汇总问题、等待用户确认；④ 最后对照 PRD 整体走查。

**与 `mf2e-page-flow` 的分工**：`mf2e-page-flow` 是「单页面」流程（布局→接口→交互→埋点→review），触发词是「开发某个页面」；本技能是「整需求」流程，覆盖需求级 PRD 汇总、多页面归类、逐页还原、整体走查。第 4 步逐页还原时，可对单个页面复用 `mf2e-page-flow` 或直接调用 `mf2e-figma-implement`。

## 触发条件

- 用户说「开发需求 / 完成一个功能 / 走完整需求开发流程」，并附带一个**资源登记文件地址**（如 `docs/README.md`，内含四类资源链接）→ 从该文件解析所需资源
- 用户直接提供「需求文档 + 交互稿 + 接口文档 + 视觉稿」四类原始材料地址，要求「开发一个需求 / 完成一个功能 / 走完整需求开发流程」
- 用户明确要从零开始完成一个跨多页面的需求

## 前置条件

- 已连接 Figma MCP（`get_design_context` / `get_screenshot` / `get_metadata`）
- 已连接模拟器 MCP（`@mf2e/simulator-screenshot-mcp`：`screenshot_simulator` / `swipe_simulator` / `compare_with_design`）
- 已连接 POPO MCP（`getContentByUrl`）——需求文档多以 popo 云空间文档提供
- `FIGMA_TOKEN` 环境变量已设置（归类脚本、截图拉取需要）
- 已获知资源地址（需求文档 / 接口文档 / 视觉稿为核心，交互稿可选），来源二选一：
  - 用户提供的资源登记文件（默认约定 `docs/README.md`，格式为每行 `- 类型：地址`）
  - 用户直接口述 / 粘贴的地址

## 资源解析（进入流程前，必做）

四类资源里，**需求文档 / 接口文档 / 视觉稿 是核心资源，交互稿可选**（`mf2e-prd-merge` 已支持「仅需求文档」模式）。缺则问、不臆测：

1. **用户给了文件地址** → 读该文件（本地路径用 Read，POPO / 在线文档用 `getContentByUrl`），按行解析「需求 / 交互 / 接口文档 / 视觉稿」四类资源地址（登记格式通常为 `- 类型：地址`，如 `docs/README.md`）。
2. **用户没给文件地址** → 不猜，直接询问用户，请其提供资源（可一次性给地址，也可给一个资源登记文件路径）。
3. **核对补齐**：解析 / 询问后，列出「已有哪些资源、还缺哪些」：
   - 缺**核心资源**（需求 / 接口文档 / 视觉稿）→ 继续向用户索取，直到齐全（或用户明确某项「没有 / 忽略」）。
   - 缺**交互稿** → 询问用户「是否需要补全交互稿」；用户确认「有则补」，或「没有 / 无需交互稿」都继续推进，第 1 步按「仅需求文档」模式执行。

> 四类资源与后续步骤的对应：需求 + 交互 → 第 1 步 PRD（无交互稿则降级为「仅需求文档」模式）；接口文档 → 第 2 步接口；视觉稿 → 第 3 步归类 + 第 4 步还原。某类资源缺失时，对应步骤按各子技能「仅 XX 模式」降级处理。

## 资源就绪后：列任务计划 + 确定输出目录

资源齐全后，**先不开始第 1 步**，向用户输出「本次要做的几步任务」（对照下方总体流程的五步，标注哪些步骤会因资源缺失而降级），并说明输出目录约定；等用户知晓后再进第 1 步。

**输出目录约定（全程固定）**：所有文档 / 中间产物统一落在 `docs/yyyy-m-d-name/`，`name` 由 `mf2e-prd-merge` 自行推断（需求文档优先、交互稿兜底，不再询问用户）。此后**每一步的文档 / 中间产物都落在这个目录下**，不再散落：

| 步骤 | 落在 `docs/yyyy-m-d-name/` 下的产物 |
|---|---|
| 1. PRD | `prd.md`、`issue.md`、`assets/` |
| 3. 页面归类 | `visual/` —— **交付物**：`manifest.json/.md`（后续还原查 node-id）；**过程数据**：`raw.json`、`classify.json`、`shots/`（收尾可清理，需要时可按 manifest 的 node-id 重新拉取） |
| 4. 视觉还原 | 页面截图对比记录（`screenshots/`） |
| 5. 走查 | `review.md` |

> 代码类产物（类型 `src/types/`、端点 `src/store/api.ts`、Store `src/store/modules/`、页面 `src/pages/`、`mock/`）仍按项目约定写进源码，不进该目录。收尾交付时可区分清理：删除归类过程数据，保留 manifest 等交付物。

## 总体流程

| 步骤 | 目标 | 调用技能 | 执行方式 | 产物 | 门禁 |
|---|---|---|---|---|---|
| 1. PRD | 合并需求+交互，产出开发用 PRD | `mf2e-prd-merge` | sub agent | `prd.md` + `issue.md` + 截图 | 所有待确认问题得到反馈 |
| 2. 接口/Store | 生成类型/端点/Mock/Store | `mf2e-api-scaffold` | sub agent（决策点前置） | types + api.ts + mock + store | 所有接口验证通过 |
| 3. 页面归类 | 归类设计稿所有页面/组件/弹窗 | `mf2e-figma-classify` | sub agent | `manifest.json` | PRD 页面/组件/弹窗全部在归类中出现 |
| 4. 视觉还原 | 逐页还原 + 截图对比 | `mf2e-figma-implement`（含导出 PNG 资源）+ `mf2e-compare-screenshot`（配 `mf2e-falcon-rn`） | 主模型主导 | 页面代码 + 对比记录 | 每页截图验收 |
| 5. 走查 | 对照 PRD 走查实现 | 独立走查 agent | sub agent | `review.md`（todo 列表） | 所有遗留问题打勾 |

> 步骤间有依赖：第 2 步依赖第 1 步确认的字段口径；第 3 步依赖第 1 步的前端范围；第 4 步依赖第 3 步的 node-id；第 5 步依赖前四步全部产物。**严格按顺序执行，不要跳步。**

## 第 1 步：输出 PRD

1. **外包给独立 sub agent** 执行 `mf2e-prd-merge`：prompt 让 sub agent 加载该 skill，用「需求文档 URL + 交互稿 URL」合并出需求交互文档（输出目录由 skill 自行推断）。截图识图用 `vision` subagent（主模型不识别图的环境）。sub agent 遇硬卡点会中断抛回，主会话收到后转达用户、解决后继续。
2. sub agent 产出 `docs/yyyy-m-d-name/` 下的 `prd.md` + `issue.md` + `assets/` 截图 + 待确认问题清单，返回主会话。
3. 主会话把待确认问题清单（按「PM / 后端 / 交互稿盲区」分组）展示给用户，等用户逐条反馈。
4. 门禁：所有待确认问题得到反馈后，回写 `prd.md` 结论，再进入下一步。

## 第 2 步：生成接口/Store

1. **主模型先探测 + 问清决策点**（决策点前置，不外包这一步）：按 `mf2e-api-scaffold` 交互层（SKILL.md）的 Step 0 探测项目约定、问清决策点（路径前缀 / 字段名口径 / 接口范围 / 冲突处理策略 / JS 类型方案等）。完整清单与口径以 api-scaffold 交互层为准，不在此重复。
2. **外包给独立 sub agent** 执行接口生成：prompt 让 sub agent 读 `.agents/skills/mf2e-api-scaffold/references/execution.md`，按入参契约传入「已确认约定 + 接口文档路径」批量生成并验证（`tsc --noEmit` + mock 服务 `curl` 核对）。sub agent 不中途问用户，遇冲突记入待决策清单返回。
3. 主会话核对 sub agent 产物（文件清单 + 关键决策点是否落实）。
4. 门禁：所有接口验证通过；无法完成验证时询问用户「协助验证」还是「延后处理」。

## 第 3 步：页面归类

1. **执行前先提醒用户**：Figma desktop MCP 只能读取**当前活跃标签**的文档，整个第 3 步期间请保持 Figma 停留在视觉稿文档（曾发生活跃标签是交互稿导致整步归类错源重跑的返工）。
2. **外包给独立 sub agent** 执行 `mf2e-figma-classify`，三阶段「提取 → 分析 → 渲染」，**产物落 `docs/yyyy-m-d-name/visual/` 目录**（脚本默认输出到当前目录，需先在该目录下运行或指定输出）：
   - 提取：先做**文档身份校验**（MCP 可见的文档/页面名必须与用户提供的 URL 声明一致，不一致直接中断抛回），再拉视觉稿顶层 frame → `raw.json` + `shots/` 截图
   - 分析：先 PRD 词表确定性匹配，未命中的交 `vision` 识图（只取证据），交叉比对定归属
   - 渲染：`classify.json` → `manifest.json`（页面分组 → node-id 列表）
3. sub agent 返回 `manifest.json` + 未归属清单；主会话把 PRD 前端范围的页面/组件/弹窗清单逐项对照 manifest，找出遗漏。
4. 门禁：所有 PRD 中需要完成的页面/组件/弹窗必须全部出现在归类汇总中；有遗漏咨询用户「手动提供 node-id」还是「延后处理」，回填 manifest。

## 第 4 步：逐页视觉还原 + 截图对比

按依赖顺序逐页执行（入口 → 深层），每页一个循环：

0. **重页面先外包「设计规格提取」**：对含多屏/多弹窗的复杂页面，先把「get_design_context 精确样式 + vision 识图布局结构 + 文案全集 + 资源清单 + 接口字段映射」外包给 sub agent，产出一份**自包含的设计规格文档**（如 `m2-design-spec.md`），主模型据此写码。规格文档一次到位可大幅降低主上下文消耗，且留档可复用；轻页面可跳过此步直接走第 1 步。
1. `mf2e-figma-implement` 拿设计上下文 + 截图（配 `mf2e-falcon-rn` 编码规范：先探测 TS/JS 再读对应 references）
2. 用 `mf2e-figma-implement` 的「导出 PNG 资源」能力（`references/export-png.md`）导出图标资源
3. 写页面代码（Page/Nav/Main/组件/注册到 `pages/index.ts`）
4. `tsc --noEmit` 类型检查
5. 截图对比：`simulator-screenshot` 截图 + `mf2e-compare-screenshot` 对比设计稿（必要时 `vision` 识图找差异）
6. 有差异 → 修复 → 再截图；验收通过 → 下一个页面

门禁：每页截图验收；无法自行截图则提示用户配合；除非用户明确「跳过截图」，否则不进入下一页。

## 第 5 步：走查

1. 另起独立 sub agent，输入「PRD 路径 + 实现代码路径」，对照走查。
2. 输出分级报告，落盘 `docs/yyyy-m-d-name/review.md`，遗漏问题用 **todo 形式**列出（`- [ ]`）。
3. 门禁：用户修复后打勾，必须所有遗留问题都打勾（可以是明确「延后 / 忽略」）才视为本次开发任务完成。

## 门禁规范（必须遵守）

**总原则**：每一步完成后，先汇总问题 → 全部确认 → 询问用户是否进行下一步 → **不自动进行下一步**。

- **Step1**：所有「待确认问题」必须全部得到反馈（用户明确的修改/忽略/待定）；若用户只回答一部分，剩下的问题**再次询问**，直到全部闭环。
- **Step2**：所有接口必须验证通过；无法完成验证时，**询问用户**是「协助验证」还是「延后处理」。
- **Step3**：所有 PRD 中需要完成的页面/组件/弹窗必须全部出现在归类汇总中；有遗漏**咨询用户**是「手动提供」还是「延后处理」。
- **Step4**：每页截图验收；无法自行截图则提示用户配合；除非用户明确「跳过截图」，否则不进入下一页。
- **Step5**：走查报告落盘 `review.md`，遗漏问题用 **todo 形式**列出，用户修复后打勾；必须所有遗留问题都打勾（可以是明确延后/忽略）才视为本次开发任务完成。

## 上下文管理约定

长流程主上下文会膨胀，靠「重步骤外包 sub agent + 文件为真相源」控住，第 4 步主模型主导、决策当场问：

1. **执行重、决策稀疏的步骤外包 sub agent**（第 1 / 2 / 3 / 5 步）：sub agent 后台跑完返回，**不能中途问用户**；prompt 固死「遇冲突不硬猜，记入待决策清单返回」，遇**无法继续的硬卡点**（读不到文档、SECTION 数量超限）**直接中断抛回**。两种情况都由主会话转达用户、收集决策后回填 / 继续。
2. **决策密集步骤主模型主导**（第 4 步逐页还原）：撞上冲突 / 字段对不上当场问用户，不外包。
3. **文件为真相源**：每步产物落盘后即为真相，主上下文只保留「产物路径 + 交接摘要」，不保留该步原始过程。
4. **门禁处是压缩点**：每步完成、产物已落盘、待确认问题闭环后，主动提示用户「上一步已落盘，可 `/compact`」。
5. **sub agent 产出可改**：产出落盘后主模型直接改（小改不必 resume），大改用 `SendMessage` + 名字 resume 它继续。

## 关键经验（坑，避免重复踩）

1. **主模型不支持图片输入**：Read 截图会被剥离，必须改用 `vision` subagent 识图。
2. **vision 识图有大量 OCR 误读**：依赖 Figma metadata TEXT dump 拿精确 characters 交叉纠正。
3. **需求文档是 HTML（POPO）**：`getContentByUrl` 返回转义 HTML，先用 Python 转 markdown 文本（保留表格）。
4. **接口文档路径前缀可能和项目实际不一致**：生成前 `grep` 项目代码找真实前缀线索，并向用户确认。
5. **`createStyles` 会做主题色映射**：某些浅色（如 `#eef1f4`）会匹配主题色表被映射成暗色黑色，用近似色避开精确匹配。
6. **渐变库可能未安装**：`react-native-linear-gradient` 若未装，渐变改用 `mf2e-figma-implement` 的「导出 PNG 资源」能力导出图片 + `ThemeImage`。
7. **`BaseSuspense` 的 `onFetch` 不能传内联箭头函数**：每次渲染新引用会导致死循环，用 `useCallback` 稳定引用。
8. **长页面 ScrollView 要加 `flex: 1`** 才能滚动；`swipe_simulator` 对 RN ScrollView 可能滚动不生效，需用户手动配合验收。
9. **Figma desktop MCP 只能读活跃标签**：涉及 Figma 的步骤执行前提醒用户保持目标文档为活跃标签；归类/还原期间标签被切走会导致节点拉取失败或整步错源。

## 收尾汇总

五步全部走完、Step5 所有 todo 打勾后，输出整体交付报告：

```
✅ 需求「<需求名>」开发完成

资源使用：需求文档 / 交互稿 / 接口文档 / 视觉稿（各地址或 nodeId）
各步产物：
- PRD：docs/yyyy-m-d-name/prd.md
- 接口：N 个端点 + M 个 store + mock
- 归类：manifest.json（X 个页面分组）
- 还原：已还原页面列表 + 截图对比记录
- 走查：review.md（todo 已全部打勾）

遗留事项（如明确延后/忽略的 todo）：
<列出>
```
