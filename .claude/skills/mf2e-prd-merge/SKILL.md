# 需求交互文档合并

## 概述

将「PRD 需求文档（非必选）+ Figma 交互稿」合并为一份**自包含**的需求交互文档（MD + 截图附件）。

**核心原则**：下游大模型只需读取这一份 MD + 同目录截图，就能完整理解需求并进入开发，无需查阅原始 Figma/PRD。

**核心约束**：
- 🔴 **不能自由发散，必须严格按照文档范畴**。需求文档和交互稿里没写的内容不能凭空添加
- 🔴 **文档范畴保持在需求层面，不能涉及具体的开发方案**。不提组件名、文件路径、API 端点、代码结构
- 🟡 需求文档 vs 交互稿有不完整、矛盾的地方，记录到待确认问题，不自行填补

## 触发条件

当用户消息中出现以下任一模式时自动加载此 Skill：
- `[需求：{url}]` + `[交互：{url}]`（简化格式，推荐）
- `需求文档地址/链接` + `交互稿地址/链接`
- `梳理需求交互文档` / `合并 PRD 和交互稿` / `需求交互文档合并`

**需求文档、交互稿至少提供一个即可触发**（两个都无则不触发）：
- 仅提供交互稿 → 走"仅交互稿"模式
- 仅提供需求文档 → 走"仅需求文档"模式（跳过 Figma 截图分析，从需求文档提炼页面模块与结构）
- 两者都提供 → 走"双通道"模式（完整流程）

## 前置条件

- FIGMA_TOKEN 环境变量已设置
- 需求文档（如有）可通过对应的 MCP 或 WebFetch 获取

## 必须遵循的 7 步工作流

> 每步末尾有质量门（QA Gate），必须通过才能进入下一步。
>
> 本 skill 可单独使用，也可被 sub agent 编排调用。执行中遇到**无法继续的硬卡点**（如需求文档读不到、SECTION 数量超限），**直接中断并把问题抛回给调用方**：单独使用 = 询问用户；sub agent 调用 = 作为返回值抛给主 agent。
>
> **正常完成时**，作为 sub agent 调用的返回值（final result）包含：`prd.md` 路径、`issue.md` 路径、`assets/` 目录，以及从 prd.md「六、待确认问题」汇总出的待确认问题清单（按「需与 PM 确认 / 需与后端确认 / 交互稿覆盖盲区」分组）。

### Step 0：确定输出目录

**操作**：
1. 推断子目录名 `yyyy-m-d-name`（如 `2026-7-21-bee-bounty`），**自行推断、不再询问用户**：
   - 有需求文档 → 优先按需求文档标题/项目名推断
   - 仅交互稿 → 按交互稿 URL 文件名推断
2. 默认放在 `{project}/docs/` 下；`docs/` 不存在则直接创建
3. 所有截图和 MD 均放在该子目录中

**完成后反馈**：无需反馈，直接进入 Step 1。

---

### Step 1：获取需求文档并提取前端相关内容（如用户提供了需求文档）

> 如用户未提供需求文档（仅交互稿模式），跳过此步，并在 Step 4 中注明「本文档仅基于交互稿分析」。

**操作**：
1. 根据 URL 域名选择读取工具：
   - `docs.popo.netease.com` → `mcp__popo__getContentByUrl`（注意是小写 `popo`）
   - `{workspace}.feishu.cn` → 飞书 MCP 或 WebFetch
   - `confluence.{domain}` → WebFetch
   - 其他 → 优先尝试 WebFetch，失败则中断抛回（无法继续）
2. 解析文档章节结构（H1/H2/H3 层级）
3. 遍历所有表格，标注每张表格归属「前端/后端/通用」
4. 提取前端相关表格的完整单元格文本

**前端识别关键词**：
- 正向：页面、弹窗、Toast、按钮、展示、跳转、写手、C端、报名、详情、列表、稿件、个人中心、账号绑定、认证、我的、移动端、RN、H5
- 反向（排除）：运营后台、管理后台、管理端、后台审核、管理员、后台配置

**完成后反馈**：「需求文档已读取完毕，共 X 个章节，Y 个表格，其中前端相关 Z 个」

**QA Gate**：
- [ ] 所有表格已列出，每表标注了「前端/后端/通用」
- [ ] 前端相关表格的完整单元格文本已保存（不要只保存摘要，下游校验 agent 需要逐行比对）
- [ ] 文档元信息已提取（标题、版本、作者）

---

### Step 2：获取 Figma Page 结构并批量截图

> 仅当提供了交互稿时执行。**仅需求文档模式**下跳过本步，并提示「当前为仅需求文档模式，跳过 Figma 截图分析」。

**操作**：
1. 从 URL 提取 fileKey + pageId（`node-id=237-1169` → `237:1169`）
2. 获取 Page 下所有 SECTION：
   ```bash
   curl -H "X-Figma-Token: $FIGMA_TOKEN" \
     "https://api.figma.com/v1/files/${FILE_KEY}/nodes?ids=${PAGE_ID}&depth=1"
   ```
3. 过滤 name 含 "BG"/"忽略" 的 SECTION（跳过）
4. 按 `absoluteBoundingBox.y` 排序得 N 个内容区域
5. **数量校验**：如果 N > 30，**中断并抛回调用方**（碎片过多、建议先在 Figma 中按业务模块合并 SECTION）——单独使用时提示用户，sub agent 调用时作为返回值抛给主 agent。
6. 逐个渲染截图（不要一次性全部，会超时）：
   ```bash
   curl -H "X-Figma-Token: $FIGMA_TOKEN" \
     "https://api.figma.com/v1/images/${FILE_KEY}?ids=${SECTION_ID}&format=png&scale=2"
   ```
7. 截图保存到 Step 0 确定的输出目录下的 `assets/` 子目录，命名 `figma_area{N}.png`

**完成后反馈**：「Figma 已读取，Page『{pageName}』下共 {N} 个内容区域：{name1}、{name2}...（已过滤 BG）」

**QA Gate**：
- [ ] 所有内容 SECTION 截图完毕，BG 已过滤
- [ ] 截图已保存到输出目录
- [ ] 每张截图 < 3MB，scale=2 高清足够
- [ ] SECTION 总数量 = N，按 y 排序正确

---

### Step 3：逐张分析截图（强制 7 项 Checklist）

> ⚠️ **这是防遗漏核心步骤**。每张截图必须逐个确认以下 7 项，全部通过后再进入下一张。
>
> **仅当提供了交互稿时执行**。仅需求文档模式跳过本步与 Step 3.5。

#### 截图分析 Checklist

| # | 检查项 | 具体操作 |
|---|--------|---------|
| 1 | **四角扫描** | 右上角、右下角、左上角、左下角是否有未被注意的**表格、状态矩阵、枚举列表**？ |
| 2 | **四边扫描** | 顶部、底部、左侧、右侧边缘是否有**批注连线指向屏幕内**？ |
| 3 | **状态矩阵** | 图片中是否包含**「全部状态」「按钮状态」「异常状态」「弹窗文案」等表格**？这些通常被误判为"装饰"而忽略 |
| 4 | **红/黄色文字** | 所有红、黄高亮文字是否都已提取？逐条区分「设计批注」vs「页面内的警示/强调」 |
| 5 | **弹窗/浮层多态** | 是否有虚线框标识的弹窗？弹窗内是否有「未通过/已通过」「待审核/已认证」等多态？ |
| 6 | **底部区域** | 图片最下方（尤其是偏右位置）往往放**辅助表格、状态汇总、设计规范、按钮状态全集** |
| 7 | **重读两遍** | 写完该区域文档后，回到图片**只看边缘区域**重读一遍，确认无遗漏 |

**QA Gate**：
- [ ] 每张截图 7 项 Checklist 已逐项确认
- [ ] 所有表格（尤其是角落的）内容已提取
- [ ] 所有状态枚举已完整列出（不含"等"、"xxx 等"）

---

### Step 3.5：Metadata TEXT 交叉比对（纠正 OCR 误读）

> 截图 OCR 容易读错品牌名、数字、特殊字符（$¥🔗*）、小字标注。
> Figma REST API 可以一次性拿到 Section 下**所有 TEXT 节点的精确 characters**，成本极低。
>
> **仅当提供了交互稿时执行**。仅需求文档模式跳过本步。

**操作**：

1. 对每个 Section 拉全量子节点并过滤出 TEXT：
   ```bash
   curl -H "X-Figma-Token: $FIGMA_TOKEN" \
     "https://api.figma.com/v1/files/${FILE_KEY}/nodes?ids=${SECTION_ID}&depth=5" \
     | python3 -c "
   import json, sys
   data = json.load(sys.stdin)
   doc = data['nodes']['${SECTION_ID}']['document']
   def extract(node):
       if node.get('type') == 'TEXT' and node.get('characters','').strip():
           return [node['characters'].strip()]
       return sum((extract(c) for c in node.get('children',[])), [])
   texts = extract(doc)
   print(json.dumps(list(set(texts)), ensure_ascii=False))
   "
   ```
   > 中间 JSON 可能几百 KB，但 Python 立即过滤为纯 characters 数组，最终只有 **~3KB / ~750 tokens**。

2. 拿到精确字符列表后，与截图分析结果做交叉比对：
   - **品牌名、产品名**：以 characters 为准
   - **数字、价格**：以 characters 为准
   - **特殊字符**（`*🔗¥>$`）：以 characters 为准，这些通常代表必填标识
   - **🤔⚠️ 标注**：以 characters 为准，截图可能遗漏小字标注
   - **按钮/状态文案**：以 characters 为准，确保全文一致
   - **空间关系、颜色、箭头**：仍以截图为准（characters 无这些信息）
   - 不一致处 → characters 胜出，差异记录到 issue.md

3. 用 characters 列表**反向检查**：截图分析中是否遗漏了 characters 里存在但 MD 未出现的文案。

**QA Gate**：
- [ ] 每个 Section 的 TEXT dump 已获取
- [ ] OCR 误读已纠正（品牌名、数字、特殊字符、标注）
- [ ] 遗漏文案已补充到 MD
- [ ] 差异已记录到 issue.md

### Step 4：合并写入 MD

**输出位置**：`{Step 0 确定的输出目录}/prd.md`

**固定章节模板**：

```markdown
# {项目名} — 需求交互文档

> 创建日期 / 项目 / 数据来源（一句话）

---

## 一、需求背景与目标
### 1.1 背景（从需求文档提取，如无则从交互稿推断）
### 1.2 目标
### 1.3 视觉稿链接（如有）
### 1.4 前端范围（本仓库交付模块 + 不在本期范围的明确排除）
### 1.5 数据来源说明（标注当前模式："基于需求文档 + 交互稿" / "仅基于交互稿" / "仅基于需求文档"）

---

## 二、全局规则

### 2.3 跨端支持范围
### 2.4 端外 H5 规则
### 2.5 术语约定（全局术语表）

## 三、模块详解

每个模块按以下结构描述：

**有交互稿时**：`[完整交互稿截图：assets/figma_area{N}.png]` + 页面结构表 + 全部状态枚举
**仅需求文档时**：基于需求文档的章节/表格提炼页面模块与结构（区域 | 元素），不引用截图

#### 页面结构
| 区域 | 元素 |

#### {其他交互细节}
#### 分歧点（需求文档 vs 交互稿不一致处，如有）

## 四、状态流转
ASCII 状态机图，含全部转移路径 + 全部节点

## 五、激励/规则摘要（如有）

## 六、待确认问题
分类：需与 PM 确认 / 需与后端确认 / 交互稿覆盖盲区

---

## 附件
交互稿截图留存于 `assets/` 目录（如有交互稿）。
```

**QA Gate（输出质量强制规则）**：

| # | 规则 | 检查方式 |
|---|------|---------|
| R1 | **零外部引用** | grep 确认无「来自 Figma 区域」「详见 POPO Table」「详见图 X」 |
| R2 | **全状态覆盖** | 任何按钮/弹窗/进度条/标签的状态枚举都完整列出，不含「等」 |
| R3 | **截图同目录** | 截图放在 `assets/` 子目录，MD 中用 `assets/figma_area{N}.png` 引用（有交互稿时适用） |
| R4 | **术语统一** | 全文术语统一，术语表已定义 |
| R5 | **分歧标记** | 需求文档 vs 交互稿矛盾处用 `> ⚠️ 需确认` 标注 |
| R6 | **独立文档** | 下游只需读此 MD + 同目录截图即可理解全部内容（仅需求文档模式下，页面级交互细节以需求文档为准） |
| R7 | **不涉实现** | 不提组件名、文件路径、API 端点、代码结构等实现细节 |

### Step 5：Sub-agent 自洽校验

**操作**：启动一个独立的 Explore sub-agent，传入：
- 产出 MD 路径
- 需求文档原始数据文件路径（如有）
- Figma 截图目录（如有）

> 本 skill 可能本身运行在 sub agent 中，Step 5 再 spawn 一个校验 agent 是「套娃」，**允许且推荐**——校验的独立视角价值不因套娃消失。
>
> 校验范围按当前模式动态调整：双通道模式对比需求文档 + 截图；仅交互稿模式对比截图；仅需求文档模式对比需求文档。

**校验命令模板**：

```
对比「需求文档原始数据（如有）」+「交互稿截图（如有）」vs「产出 MD」，逐项检查：
1. 状态枚举是否遗漏（尤其按钮态、稿件态、认证态）
2. 按钮/Toast/弹窗文案是否完整
3. 跳转流程/Schema 是否一致
4. 术语是否统一
5. 需求文档或交互稿提到但 MD 未覆盖的内容
6. 需求文档 vs 交互稿的矛盾是否已标记
7. MD 中是否有超出文档范畴的"自由发挥"内容

输出：分级报告
- 严重（必须修复的矛盾/遗漏）
- 中等（建议修复的不一致）
- 轻微（文案/格式优化）
- 补充建议（有价值的遗漏内容）
```

**QA Gate**：
- [ ] 校验报告已生成
- [ ] 严重问题已修正并回写到 MD
- [ ] 中等问题视情况修正或标注待确认

---

### Step 6：输出校验报告 + 最终修订

**操作**：
1. 将校验报告写入 `issue.md`（与 `prd.md` 同级）
2. 在 `prd.md` 末尾追加校验报告引用链接
3. 最终确认 R1-R7 全部通过

**QA Gate**：
- [ ] 输出文件清单：`prd.md` + `issue.md` + `assets/` 截图目录（有交互稿时产出截图目录）
- [ ] 全部文件在同一子目录下
