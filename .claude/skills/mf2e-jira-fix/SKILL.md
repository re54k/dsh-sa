# MF2E Jira Fix Skill

NEWSH5（传媒前端）团队的 Jira 修 bug 工作流。基于通用的"读任务 → 修代码"流程，叠加了本团队的**名词对齐**、**列表确认**和**修复后回写与留痕**三个环节。

- 认证与配置：skill 目录下 `config.conf`（chmod 600，凭据由用户自己填），环境变量 `JIRA_FIX_BASE / JIRA_FIX_USERNAME / JIRA_FIX_PASSWORD` 可覆盖。配置缺失时脚本以 `ERROR_CONFIG_MISSING` / `ERROR_CONFIG_INCOMPLETE` 报错，此时停下引导用户：
  > 请复制模板并填写：`cp <skill目录>/config.conf.example <skill目录>/config.conf`，填入 jira_base / username / password 后 `chmod 600 <skill目录>/config.conf`，然后告诉我。
- 不要替用户填凭据，不要把密码打印到对话/日志/提交信息里。
- 命令统一从 **skill 实际安装目录**执行：`node <skill目录>/scripts/jira.js <子命令>`。

## 名词对齐（本团队约定，脚本已内置为默认值）

**状态**——用户嘴里的说法与 Jira 状态字段的对应关系：

| 口语说法 | Jira 状态实际值 | 说明 |
|---|---|---|
| 待办 | 开始、重新打开 | 两个状态都算待办；JQL 里需按状态 ID 检索（脚本已处理，勿手拼状态名 JQL） |
| 处理中 | 开发中 | 修复完成后流转到这里 |
| 待测试 | 待测试 | |
| 测试中 | 测试中 | |
| 待发布 | 待发布 | |
| 已发布 | 已发布 | |

**类型**——"bug"和"需求"的归类：

| 归类 | Jira 类型 |
|---|---|
| bug | 改进、故障、线上问题 |
| 需求 | 故事、任务 |

用户说"改 bug / 修 bug"时只处理 bug 类型的任务。

**按状态检索**——用户问的不是"待办"时，用 `list --status <状态>` 指定（多个状态逗号分隔），其余过滤规则（类型、经办人、项目）不变：

- "我处理中的 bug" → `--status 开发中`（排查自己手上没收尾的）
- "待测试的有哪些" → `--status 待测试`（看测试消化情况）
- "被打回来的 / 被打回的 bug" → `--status 重新打开`——常意味着上次修复没修好，优先处理；修复时先看评论里测试为什么打回

这些名词对齐直接写死在脚本里（`ALIGN` 常量），config.conf 只管连接凭据，团队流程变了就改脚本里的 `ALIGN`。

## 工作流

> **铁律：列表默认只列"分给当前登录用户"的 bug。** 这是本团队的常规诉求——大多数时候用户要清自己的待办。除非用户**明确说**"所有""全部""大家的""不限"或指定了某人（如"张三的 bug"），否则一律不加 `--assignee all`、不加 `--assignee 张三`，就用脚本默认值（`assignee = currentUser()`）。用户只是说"有哪些 bug""相关 bug 有哪些"这类模糊措辞时，**仍然算作没指定范围**，必须默认只列自己的。

### 第一步：确定要修哪个（列表 → 用户确认）

这是本 skill 的默认入口。**除非用户给了明确 ID，否则一律先拉列表、等用户确认，不要自作主张直接开修。**

按用户输入分三种情况：

1. **没有额外输入**（比如只说"改bug""看看待办"）——拉默认列表给用户挑：
   ```bash
   node <skill目录>/scripts/jira.js list
   ```
   默认范围：NEWSH5 项目 + bug 类 + 待办状态（开始/重新打开）+ **分给当前登录用户**的前 10 条。把结果整理成简表（ID、类型、优先级、标题、经办人）展示给用户，问要修哪几个。

   **默认只列"分给当前用户"的 bug**，这是本团队的常规诉求——大多数时候用户是要清自己的待办。但用户明确说"看看所有的""团队全部的 bug"时，加 `--assignee all`；用户说"张三的 bug"时，加 `--assignee 张三`。

   **换项目**：默认查 NEWSH5；用户说"看看 XXXX 项目的 bug"时，加 `--project <项目key>`（如 `--project NBS`）。状态/类型/经办人的过滤规则不变。

2. **用户给了关键字**（比如"龙虾捏形象"）——按关键字过滤后再确认：
   ```bash
   node <skill目录>/scripts/jira.js list --keyword "龙虾捏形象"
   ```
   关键字匹配标题或描述。**同样默认只列分给当前用户的**（见上文铁律——"龙虾捏形象相关 bug 有哪些"这种话不算指定范围）；只有用户明确说"所有/全部"才加 `--assignee all`，指定了某人就加 `--assignee 姓名`。同样展示列表让用户确认要修哪些。搜不到就如实说，并建议放宽关键字（换同义词、去掉修饰词）。

3. **用户给了明确 ID 或链接**——跳过列表，直接进入第二步。链接（如 `https://jira.ws.netease.com/browse/NEWSH5-123`）从中提取 `NEWSH5-123` 这样的任务 ID。

### 第二步：拉任务详情，吃透问题

```bash
node <skill目录>/scripts/jira.js get <ISSUE_KEY>
```

输出 JSON 包含 summary / description / comments / attachments（已下载到持久目录，图片用 Read 工具看）/ bug_cause（bug原因字段当前值）等字段。只想看内容不看截图可加 `--no-attachments`。

理解 bug 时：描述常为空，**务必用 Read 看附件截图**（复现步骤常在截图里），再综合评论。用一句话复述 bug 根因，这句话后面回写"bug原因"时直接可用。

### 第三步：在当前项目定位并修复

**定位从截图和描述里的硬线索来，不从标题猜。** 优先级从高到低：

1. 附件截图里的控制台报错堆栈——文件名、组件名是最精确的线索，直接按文件名/其中的标识符 Grep。比从标题猜关键字靠谱得多，堆栈指向的就是出问题的代码。
2. 截图地址栏的页面 URL / 描述里的操作路径——映射到路由或工程目录，先锁定大致范围再搜。
3. 以上都没有，再用任务标题里的功能名/组件名 Grep/Glob，尝试多个同义关键词。

找到之后的修复纪律：

1. 先 Read 目标文件理解上下文，再 Edit 修改，不要盲改。
2. 能跑测试/起服务就验证；验证不了就清楚说明改了什么、为什么、如何手动验证。
3. 搜不到相关代码就**如实告诉用户**搜过哪里、用了什么关键词，问代码实际在哪个仓库，不要硬改无关文件。

### 第四步：修复完成后回写 Jira

每个 bug 修完（代码改动落地后），把该任务流转到目标状态并填写 bug原因：

```bash
node <skill目录>/scripts/jira.js finish <ISSUE_KEY> --cause "<一句根因>"
```

- `--cause` 必填，内容就是第三步里复述的根因（中文、一句话说清为什么出这个 bug，例如"列表复用时未重置滚动位置导致条目错位"）。
- **默认自动流转到"开发中"（口语"处理中"）**：修完 bug 后直接执行 finish，不用问用户流转到哪里。执行完**告知用户**已经流转到"开发中"并填了原因。
- **用户明确指定状态时跟着走**：用户说"拖到待测试""流转到已发布"这类话，就加 `--to <状态>`（支持待测试/测试中/待发布/已发布等任意状态名，脚本会匹配对应的 transition）：
  ```bash
  node <skill目录>/scripts/jira.js finish <ISSUE_KEY> --cause "<一句根因>" --to 待测试
  ```
- 脚本行为：**先看目标流转的屏幕是否含 bug原因 字段**（`expand=transitions.fields`），再决定怎么写入——含就随流转一次性写入（`cause_written_via: transition`）；不含就流转后单独 PUT 字段（`field_update`），PUT 也写不上就兜底加 `【修复原因】`评论（`comment`），保证原因一定留痕。实测本 Jira：流转到「开发中」的屏幕**不含**该字段（走兜底），流转到「待测试/测试中/待发布/已发布」的屏幕**含**该字段（随流转写入）。脚本自动适配，无需人工判断。
- 任务已在目标状态时脚本会**跳过流转、只补写原因**（幂等）——finish 执行到一半失败后可以放心重跑。
- **任务已有 bug原因 时注意覆盖语义**：get 输出里的 `bug_cause` 若已有值（二次修复、测试打回重修都会遇到），finish 会直接覆盖它。此时 --cause 写清**本次**的原因（必要时带上"二次修复/回归"字样），旧值如仍有价值，先用 comment 子命令留痕再 finish。
- 不确定会不会流转成功时，可先 `--dry-run` 只看将执行的动作，不做任何写操作。
- **多个 bug 的节奏**：用户一次确认了几个，就逐个走第二~四步——每个修完简报一句（改了什么 + 已流转已填原因），**紧接着继续下一个**，不要修一个就停下来等指示；全部完成后再给一个总汇报。多个都修完了别漏 finish。

### 评论（comment）

修复过程中需要留痕、但又不属于"修完回写"的时刻，用 comment 往任务上加评论：

```bash
node <skill目录>/scripts/jira.js comment <ISSUE_KEY> --text "<评论内容>"
```

典型场景：复现不了、需要测试补充操作路径或环境信息；修复方案有取舍要说明；测试打回后解释为什么这么改；旧 bug原因 被 finish 覆盖前的留痕。

## 工作要点

- **先确认后动手**：列表和关键字模式下必须等用户挑完再修；只有用户给了明确 ID 才可以跳过确认。
- **失败别硬刷**：登录失败（退出码 3）先让用户确认凭据，连续重试可能触发账号锁定。退出码含义：1 参数错误 / 2 配置缺失 / 3 登录失败 / 4 请求失败（网络、任务不存在、无权限、字段不可写）。
- **凭据安全**：密码不进对话、不进日志、不进 git。config.conf 保持 600（`.gitignore` 已包含）。
- **如实汇报**：没找到代码、改不动、验证不过、finish 失败，都直说，不要假装完成。
