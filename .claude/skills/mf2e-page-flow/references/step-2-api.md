# 第 2 步：生成接口与 Mock

## 目标

从第 0 步筛选出的**目标页面接口**，用 `mf2e-api-scaffold` 生成接口类型定义、API 端点、Mock 数据、Store 模块，为第 3 步的数据对接准备好"数据层"。

## 输入与输出

- **输入**：接口文档（本地 `docs/*.yaml|.md` 或远程 gotest 等 URL）
- **输出**：类型定义（`src/types/`）、API 端点（`src/store/api.ts`）、Mock（`mock/`）、Store 模块（`src/store/modules/`）

## 编排的子技能

| 子技能              | 在本步的职责                                           |
| ------------------- | ------------------------------------------------------ |
| `mf2e-api-scaffold` | 探测项目约定 → 解析接口文档 → 生成类型/端点/Mock/Store |

## 执行流程

### 2.1 获取并筛选目标页面接口

> **关键**：接口文档通常覆盖**整个项目**，直接全量生成会把别的页面的接口也做进来。必须先筛出目标页面的接口，再交给 `mf2e-api-scaffold`。

1. **读取接口文档**（读取方式按第 0 步 0.1 的地址类型选择）：若接口文档是网页且无法直接解析成接口定义，提示用户导出为 `.yaml` / `.md` 文件放到 `docs/` 下再继续

2. **按目标页面锚点筛选接口**（锚点来自第 0 步），筛选依据：
   - OpenAPI 的 `tags`（模块分组）里与页面名/模块名匹配的分组
   - 路径前缀（如 `/rank`、`/task-center`）与页面路由相关
   - 接口名 / `operationId` / 注释里出现页面名
   - 需求文档（第 5 步才用，但可提前交叉印证）里该页面提到的接口

3. **产出目标接口清单**，列给用户确认（尤其边界模糊时）：

   ```
   📋 目标页面「<页面名>」接口清单
   1. GET  /api/v1/rank          排行榜列表
   2. POST /api/v1/rank/toggle-public  公开/匿名切换
   ```

   > 拿不准某接口是否属于本页面时，向用户确认，不要猜，也不要默默漏掉。

### 2.2 编排 `mf2e-api-scaffold` 生成

加载 `mf2e-api-scaffold` 技能，按其完整流程执行，但把**输入范围限定为 2.1 筛选出的目标接口**：

1. **Step 0 探测项目约定**（语言 TS/JS、API 端点文件、fetch 封装、Mock 服务、Store 模式、类型目录）——探测结果先向用户简要汇报
2. **解析接口文档**，只提取目标页面接口的 method、路径、参数、响应结构
3. **命名推断**（operationId 优先，遵循项目现有风格）
4. **生成类型定义** → `src/types/`
5. **添加 API 端点** → `src/store/api.ts`
6. **生成 Mock** → `mock/`（`{METHOD}.js` + `res.json`）
7. **生成 Store 模块** → `src/store/modules/`
8. **验证**（见 2.3）

> 生成细节（类型映射、分页模式、响应包装识别、Mock 目录规则等）以 `mf2e-api-scaffold` 技能为准，这里不重复。核心是：**只生成目标页面的接口，不要全量生成。**

### 2.3 验证

按 `mf2e-api-scaffold` 的 Step 7 验证：

1. TS 项目跑类型检查（`tsc --noEmit` 或 `package.json` 的 `typecheck` 脚本）
2. 启动 mock 服务（`npm run dev` 等，以 `package.json` 为准；已在运行则重启以加载新 mock）
3. 对每个新接口 `curl` 一次，核对响应包装结构、字段完整性、字段类型；不一致就修正 `res.json` 或类型定义后重验

### 2.4 本步出口条件

满足以下全部条件后，输出第 2 步验收摘要并**停等用户确认**，用户确认后才进入第 3 步：

- [ ] 目标接口的类型 / 端点 / Mock / Store 已生成（仅目标页面接口）
- [ ] TS 项目类型检查（`tsc --noEmit` 或 `typecheck`）通过
- [ ] 每个新接口 mock 已 `curl` 验证：响应包装、字段、类型与文档一致
- [ ] 验收摘要已输出：接口清单、类型名、Store hook 名、Mock 目录

**前置：第 1 步验收通过后本步才可开工；未获得用户确认，禁止开始第 3 步。**

## 与后续步骤的衔接

- 记录**生成的 Store hook 名**（如 `useRankStore`）与**接口清单**，第 3 步要在组件里调用它们绑定数据
- 记录**类型名**（如 `RankData`、`RankItem`），第 3 步渲染数据时用它约束字段
- 若本步因接口文档缺失而跳过，第 3 步只能做交互逻辑，数据绑定留待接口文档补齐后补做——在报告中标注
