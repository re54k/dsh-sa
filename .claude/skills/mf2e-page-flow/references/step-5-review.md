# 第 5 步：整体 Review

## 目标

对照需求文档，逐条排查前面四步实现的功能是否有遗漏或偏差，并修正，确保交付的页面完整满足需求。

## 输入与输出

- **输入**：需求文档（目标页面部分）+ 前四步的全部产物（布局、接口、交互、埋点）
- **输出**：需求核对报告 + 修正后的代码

## 执行流程

### 5.1 获取并筛选目标页面需求

1. **读取需求文档**（读取方式按第 0 步 0.1 的地址类型选择）
2. **按目标页面锚点筛选**（锚点来自第 0 步）：提取目标页面的需求条目——功能点、展示规则、交互要求、边界/异常处理
3. **列需求核对清单**（这是 review 的基准）：

   ```
   📋 目标页面「<页面名>」需求核对清单
   1. 展示排行榜列表，包含排名/昵称/收益字段
   2. 支持公开/匿名两种模式切换
   3. 未登录时展示引导登录态
   4. ...
   ```

### 5.2 逐条核对实现

对照需求清单，逐条检查实现是否满足，重点维度：

| 维度       | 核对内容                                     |
| ---------- | -------------------------------------------- |
| 功能完整性 | 需求列的每个功能点是否都实现了               |
| 展示内容   | 字段/文案/数据是否与需求一致                 |
| 交互行为   | 点击/跳转/弹窗/刷新是否符合需求描述          |
| 边界与异常 | 空态、加载态、错误态、未登录态是否覆盖       |
| 视觉还原   | 是否保持第 1 步的视觉还原（未被第 3 步破坏） |
| 埋点覆盖   | 需求里提到的统计点是否都已埋（若有埋点文档） |

输出核对结果，逐条标注 ✅ / ❌ / ⚠️（部分实现），差异处写清楚「需求是什么 → 实现是什么 → 怎么改」。

### 5.3 修正偏差

对 ❌ / ⚠️ 项立即修正：

- 功能遗漏 → 补齐对应实现（可能回到第 2/3/4 步补接口、交互或埋点）
- 行为偏差 → 按需求描述改正交互逻辑
- 视觉偏差 → 回到第 1 步截图校验流程修正样式
- 修正后重新核对，直到需求清单全部通过或剩余差异明确记录

### 5.4 输出 Review 报告

```
📋 Review 报告：页面「<页面名>」
- 需求条目总数：N
- ✅ 通过：P 项
- ❌ 修正：Q 项（<简述修了什么>）
- ⚠️ 遗留：R 项（<记录原因与后续建议>）

结论：<是否满足需求、遗留项是否阻塞上线>
```

### 5.5 流程收尾

- Review 报告输出后，再输出 SKILL.md「收尾汇总」中的完整交付报告，流程结束
- 前四步的验收摘要、跳过项（如埋点）、遗留差异必须体现在交付报告中

## 常见陷阱

- **只对代码不对需求**：review 的基准是需求文档，不是"代码能跑就行"。
- **跳过边界/异常态**：空态、加载态、错误态是最容易漏的，需求里哪怕一句"无数据时展示空状态"也要实现。
- **改了视觉不自知**：第 3/5 步改动后要确认没破坏第 1 步的视觉还原。
- **需求文档全项目范围**：只核对目标页面的需求，别的页面需求不管。
